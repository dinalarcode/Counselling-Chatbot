# How Bible Verse Retrieval Works (RAG Pipeline)

## Overview

The chatbot retrieves Bible verses using an advanced **Retrieval-Augmented Generation (RAG) pipeline** that combines vector similarity search with LLM reasoning. The entire system lives in `core/vector_db.py` inside the `VectorDBManager` class, and is called by `rag_engine.py`.

```
User Utterance & Intents
    ↓
┌─────────────────────────────────────────────────────┐
│      retrieve_verse_with_llm(intents, user_input)   │
│                                                     │
│  Layer 1: Intent-Based Query Construction            │
│    intents + BIBLICAL_SYNONYMS → query               │
│                                                     │
│  Layer 2: FAISS Semantic Search (Oversampled)       │
│    query → embed → L2 search → 30 candidates        │
│                                                     │
│  Layer 2.5: Chapter Diversity & Exclusion Filter    │
│  skip excluded books → cap 2/chapter → top 10       │
│                                                     │
│  Layer 3: LLM Reranker                              │
│    prompt(10 candidates, user context) → top 1 verse│
└─────────────────────────────────────────────────────┘
    ↓
Bible Verse (reference + text) injected to chatbot
```

---

## The Knowledge Base: Enriched Context Embedding

Instead of embedding raw, isolated verses, the system embeds an **enriched text**.
1. `data/verse_retrieval/alkitab_tb_enriched.csv` is generated by prepending **theological chapter summaries** to every verse.
2. Example: `[Konteks: Kejadian 1 - Penciptaan langit dan bumi...] Pada mulanya Allah menciptakan...`
3. This enriched text is embedded into a **384-dimensional vector** using `paraphrase-multilingual-MiniLM-L12-v2`.
4. FAISS searches against these context-rich embeddings, leading to much higher theological relevance. The raw verse text is preserved in metadata for display.

---

## Layer 1: Intent-Based Query Construction

**Goal**: Build a clean, theologically focused FAISS query using only classified intents and their mapped biblical vocabulary — deliberately excluding raw user keywords to prevent semantic noise dilution.

**Input**:
- `intents` — detected intent strings from LABAN

**Process**:
1. **Intent strings**: Concatenated directly as the first part of the query.
2. **Biblical Synonyms**: For every detected intent, append a predefined string of formal biblical words. (e.g., if intent is "Menyatakan Perasaan Sedih dan Kehilangan", the synonyms injected are `"dukacita ratap tangis meratap bersedih perkabungan berkabung kehilangan air mata..."`).
3. The `combined_query` is built strictly from `intent_part + synonym_part`.

> **Design decision**: Raw `user_input` (e.g., "kak aku kesel banget sama pacar") is **not** fed into the FAISS vector query. Informal slang would introduce noise into the embedding space and pull results away from relevant biblical text. Instead, `user_input` is routed exclusively to the LLM reranker (Layer 3) where the LLM can reason about conversational context.

---

## Layer 2 & 2.5: FAISS Semantic Search & Chapter Diversity

**Goal**: Find the best candidate verses while ensuring theological variety across different chapters.

**Process**:
1. The `combined_query` is embedded into a vector.
2. FAISS performs an L2 distance search. Instead of fetching just 10 results, it fetches an **oversample pool** (`k * OVERSAMPLE_FACTOR`, e.g., 30 results). The results are sorted by L2 distance (lowest = most similar).
3. **Session-Level Exclusion** (book-level): The `SessionManager` passes in a set of `excluded_books` (abbreviated book names of books already used in the current counseling session). All candidates from an excluded book are completely skipped — this operates strictly at the book level to prevent the same book from being cited more than once per session.
4. **Call-Level Diversity** (chapter-level): The oversample pool is iterated in score order. A candidate is only admitted to the final list if its **book + chapter** key has appeared fewer than `MAX_PER_CHAPTER` (default: 2) times so far. This prevents the enriched-index embedding clusters (caused by similar chapter summaries) from flooding the candidate list with verses from the same chapter.
5. **Chapter Key Extraction**: Each candidate's chapter key is built preferentially from FAISS metadata (`book_name` + `chapter` integer fields). If metadata is absent, the static helper `_extract_chapter_key(reference)` parses the reference string by splitting on `:` to drop the verse number — correctly handling both standard names (`"Mazmur 34:18"` → `"Mazmur 34"`) and numbered book names (`"1 Yohanes 4:8"` → `"1 Yohanes 4"`).
6. The filter stops once **10 diverse candidates** are collected and passed to the LLM reranker.

> **Why chapter-level instead of book-level?** The enriched `alkitab_tb_enriched_groq.csv` index creates dense semantic clusters around chapters with similar theological themes (e.g., all Psalm 119 verses cluster together because they share the same chapter summary). A book-level cap of 2 still allowed 2 verses from Psalm 119 to dominate a slot. A chapter-level cap of 2 distributes candidates more broadly across the Bible, giving the LLM reranker a more diverse pool to reason over.

---

## Layer 3: LLM Reranker

**Goal**: Use LLM reasoning to select the absolute best verse for the user's specific conversational context.

**Process**:
1. The 10 diverse candidates (with their references and raw texts) are formatted into a numbered list.
2. An LLM (Gemini/Groq/OpenAI, reusing the chatbot's backbone) is prompted with the user's utterance and the candidate list.
3. The LLM is instructed to act as a verse selector, choosing the most comforting and relevant verse **without altering a single word of the text**.
4. The LLM outputs the chosen reference and text (e.g., `Mazmur 34:18|TUHAN itu dekat...`).
5. The system validates the output against the FAISS candidate list and returns the final verse to be injected into the counselor's prompt.

## Data Flow Diagram

```
alkitab_tb_enriched.csv (verses + chapter summaries)
        ↓ [one-time build]
    MiniLM Embedding
        ↓
    FAISS Index (saved to disk)
        ↓ [every query]
    retrieve_verse_with_llm(intents, user_input, excluded_books)
        │
        ├── [Layer 1] Intents + Keywords + Synonyms → Query
        │
        ├── [Layer 2] Embed Query → FAISS L2 Search → 30 Candidates
        │
        ├── [Layer 2.5] Filter Out excluded_books (book-level) → Cap 2/chapter → 10 Diverse Candidates
        │
        └── [Layer 3] Prompt LLM Reranker → Select 1 Best Verse
                │
                ↓
        { reference: "Mazmur 34:18", text: "TUHAN itu dekat...", book_abbr: "Mzm" }
```

## Key Files & Constants

| File / Constant | Role |
|---|---|
| `core/vector_db.py` | `VectorDBManager` class — builds enriched index, runs search and diversity filters |
| `core/rag_engine.py` | Connects FAISS output to the main counseling LLM chain |
| `core/session_manager.py` | Tracks `used_verse_books` to prevent intra-session repetition |
| `config.py` → `EMBED_MODEL` | `paraphrase-multilingual-MiniLM-L12-v2` |
| `OVERSAMPLE_FACTOR` | `3` (Fetches 30 raw FAISS candidates before filtering) |
| `MAX_PER_CHAPTER` | `2` (Max 2 verses from the same book+chapter in the top 10) |
| `_extract_chapter_key(ref)` | Static helper — parses reference string into `"book chapter"` key (e.g. `"1 Yohanes 4:8"` → `"1 Yohanes 4"`) |
